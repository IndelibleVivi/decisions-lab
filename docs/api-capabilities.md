# 把 API 能力变成可证伪的实验

研究对象是 Decisions API 及相邻原生接口：它们能接收什么、怎样组织问题、返回什么对象，以及这些对象允许怎样被代码使用。每个方向都从一条具体的能力依据出发，给出能区分解释的对照。网站的卡带和画面不承担能力证据。

[2026-10-22 核查](../research/2026-10-22/README.md)拥有本轮来源与版本；[能力索引](../catalog/capabilities.json)把依据、假设、请求覆盖和结果状态连起来；[实验说明](../experiments/api-capabilities/README.md)拥有可运行命令和记录格式。前 3 组是本轮离线实现范围，后 4 组是有具体对照的后续研究设计。所有 provider 结果均为 `NOT_RUN`。

## 证据怎样走到结果

先确认原生契约，再生成输入与本地真值，最后准备请求、导入原始响应并评分。题本答案不进入请求；请求快照和评价分别保存。一个请求包含多题时，每题自己的类型、拒答与解析错误分别记录；请求级 usage 不能复制成每题都花了同样费用。

比较时同时保留四类对象：输入和干预；原生请求与响应；真值及其生成规则；指标和最小反例。缺失结果不等于概率 0，拒答不等于 unknown。外部导入证明有一份待解释的响应文件，不证明本项目曾发出网络请求。

旧 next-action、typed-values 与新能力题本各自保留当前用户和结果契约。通用多问题实验不再受 next-action 的固定动作约束。Clairic 的 scalar、null 与预测区间仍按自己的类型解释。

## rule-compile

**一次 Choice 能否把自然语言规则编译成一个有界程序？**

两个布尔变量有 16 种函数。固定输入顺序为 `00, 01, 10, 11`，每个函数可用 4 位真值表表示。“A 已完成且 B 未完成时发出信号”对应 `0010`。候选是预先定义好的数据，代码只查表，不执行模型生成的代码。

同一条规则有两种请求结构：一次 Choice 选择整个函数；把四个状态分别作为四道题打包。对每种结构再改变等义表述、否定位置、变量名、候选顺序与不透明候选 ID。题本应覆盖整个函数空间，并提供完整规则和欠说明规则。

“只有 A 成立才允许触发”只给必要条件，仍容许 4 个函数。这里的正确行为是选择显式的 `insufficient`，不能强行挑一个真值表。它是任务选项，与 provider refusal 分开。

评分包括完整函数正确率、四状态 Hamming 错误、等义表述一致性、顺序与 ID 对照、欠说明识别。失败报告列出使函数出错的最小状态，例如 `A=1, B=1`。单次编译错误影响后续多少输入，应从选中的函数逐项计算。

24 条完整规则的两个基本结构是 48 请求、120 道问题；干预、重复和欠说明另计，实际准备数量以 CLI 输出为准。三个变量有 256 个函数，超过 OpenAI 单 Choice 的 255 个选项；两级选择与受限 DSL 属于下一组实验，不能拿未经测试的分解方式填补这次能力边界。[OpenAI 原生契约](https://developers.openai.com/api/reference/resources/decisions/methods/create/)

## probability-composition

**原生概率在换菜单、拆分事件和组合问题后，还能保留什么含义？**

三个数必须分开：输入世界定义的事件概率；模型选中的数值答案；模型为该数值选项返回的选择概率。比如世界中的 `P(red)=0.6`，正确数值答案是 `0.6`，而这个答案被选中的原生概率可以接近 `1`。`confidence` 也不自动充当事件概率。

第一组对照把互斥穷尽的 `A/B` 改成 `A1/A2/B`，明确 `A=A1∪A2`。比较粗菜单的 `r(A)` 与细菜单的 `r(A1)+r(A2)`；同时保留任务真值和原生分布，观察槽位竞争。一个纯数学负对照：原权重为 `0.6/0.4`，若拆出的两项各复制 `0.6` 再归一化，A 的总质量会变成 `0.75`。这只是可产生漂移的一种机制，不是 API 实测。

第二组用两个精确世界：`00/11` 各一半，以及 `01/10` 各一半。两者的 `P(A)=P(B)=0.5`，`P(A≠B)` 却分别是 0 和 1。分别询问、同请求打包、直接选联合状态，再由代码计算边缘值；同一题在这几种组织下的语义保持不变。

指标同时报告真值误差与一致性，例如 `P(A∧B)≤min(P(A),P(B))`、`P(A∨B)=P(A)+P(B)−P(A∧B)`。候选分布和数值答案分别检查，不能因为一组数更自洽就断言它更准确。完整分布的线性可行性检验可参考 [Dutch Books for Language Models](https://arxiv.org/html/2609.02797v1)；本轮不宣称实现了论文全部检验。

## visual-criteria

**把图片放进 criteria，是否能在请求中即时定义一种关系类别？**

Jev 允许图片出现在 `state`、`instructions` 与 `criteria`。原生格式是顶层 `assets`，正文中引用 asset key；需要 `TypeSafe-Danger-Zone-Images: true`。当前文档要求 PNG/JPEG，每边 280–1568 px，并有单图、原始请求与引用展开后的体积限制。这是实验能力，格式和质量都可能变化。[Jev 图片契约](https://docs.typesafe.ai/images)

程序生成 24 个目标，包含、接触、分离各 8 个。颜色、背景、尺寸和位置变化，几何关系由坐标计算。K1/K2/K3 使用不带关系语义的 ID。对同一批目标准备文字标准、图片标准、文字加图片、交换图片定义 4 组，共 96 请求。

交换图片时保留标签，真值随新的定义映射；模型若仍追随旧标签就会暴露错误。图片 asset 的 key、文件名和 state 不得直接写出目标关系；图片参照中也不能夹带答案文字。比较正确率、定义交换后应有的翻转、无关视觉变化的稳定性，并保存可查看的目标与参考图。

这个接口利用的是“图像作为原生判断标准”。OpenAI 支持图像输入，不等于拥有同构的 criteria asset 接口。请求准备器应明确拒绝不支持的 route。Box 是后续扩展：需另测目标存在性和坐标质量，不能把一个总会返回坐标的接口视为“已找到目标”。

## semantic-features

**一组问题的答案，能否成为可复用的语义表征？**

第一方 cookbook 用 LLM 提议问题、Jev 输出数值特征、CatBoost 预测酒评分数，再由开发集误差更新问题。其结果来自历史 `jev-1.12`，是作者报告。[官方方法与版本](https://docs.typesafe.ai/cookbooks/autoresearch_feature_discovery)

Lab 的对照应保留：直接判断最终分数；固定人工问题库；一次自动提议；根据开发集错误迭代；embedding 配合同预算监督模型。比较 4/8/16/32 题，以及只读均值、均值加离散程度、完整分布三种编码。样本按来源分组留出，测试标签不进入提议和修订循环。

主要指标是留出 RMSE/MAE、特征冗余、跨样本复用、实际请求和问题数、usage 与延迟。问题更多但误差没有改善，或只改善开发集，都能否定有益迭代的解释。**状态：研究设计；尚无数据集接入、训练器、自动 proposer 或 live 实验。** 引入 CatBoost/embedding 之前，先以现有依赖可实现的监督基线检查是否有必要。

## semantic-addressing

**相同证据换一种树结构，是否改变寻址能力？**

Choice 可以返回段落 ID。官方 line-by-line 示例同时使用 218 个行 ID 和一个 Noul 存在性判断，避免“没有答案时也会有第一名”。层级示例用边分数的几何平均排序路径；它首先是搜索分数，叶子概率的解释还需额外依据。[行寻址](https://docs.typesafe.ai/cookbooks/semantic_find) · [层级搜索](https://docs.typesafe.ai/cookbooks/hierarchical_classification)

原创题本可固定 128 段，覆盖单段答案、必须结合两段、近义但错实体的干扰、完全无答案。保持叶子文本不变，比较平铺 Choice、逐段 Predicate/Noul、单路径分层、保留多分支；树结构分别按语义、随机平衡和不平衡组织。

评价证据召回、无答案误报、最终选择、正确路径首次被剪除的位置，以及实际计算量。多段问题用证据集合评分，不能拿单选准确率冒充完整证据召回。**状态：研究设计；新 runner 可表达问题原语，文档生成、检索控制器与树搜索实验尚未实现。**

## typed-distributions

**列表与预测分布能否经得起表示变换？**

列表题本要区分所有名字的出现、不同的人、当前有效参与者。例如林遥、周岚当前有效，陈宁已退出，林遥重复出现。这些列表的重复、顺序和实体状态不同。改变提及顺序、增加重复、撤回退出状态；分别检查遗漏、误纳、顺序与重复语义。官方 list 的输入顺序声明不自动决定某个字段要求的是哪一种集合。[Clairic 字段族](https://developers.cloudflare.com/changelog/post/2026-10-19-clairic-workers-ai/)

预测题本使用固定生成器和真正留出的未来值。对同一序列做乘 10、加常量、换单位；同时变更输出网格、一步与多步 horizon。正比例变换下，理想参照为 `Qα(aX+b)=aQα(X)+b`，`a>0`。将单位不稳定、网格误差、预测误差分别计分，比较 coverage、pinball loss、区间宽度与简单时间序列基线。

厂商说明远期预测会趋向平均、陌生数据区间可能偏窄；这些是待检验假设。**状态：研究设计；既有 typed-values 只处理当前题本的 text/number/date/estimate，非空 list/forecast/time/datetime 尚未接通。** 请求参数白名单和响应处理扩展应随这些题本一起实现，不因官方支持就宣称本地已支持。

## temporal-decisions

**输入随时间到达时，模型和事件处理各自错在哪里？**

Live 文本方向先固定原创前缀：“把风扇打开……之前，先确认电源。”给每个前缀独立标签，比较断句、块大小、证据达到充分状态的时刻和后续修正。真实事件阶段再检查 `source_event_id`、合并 delta、乱序到达与旧结果覆盖，语言判断延迟和传输调度延迟分别报告。[Live 原生 Decisions 集成](https://developers.openai.com/api/docs/guides/decisions-voice)

Clef-Omni 方向用原创短片比较灯亮前响、灯亮后响、有声无灯、有灯无声。对照完整音视频、仅视频、仅音频、文字转写，并移动音轨、改变事件持续时间。评价跨模态次序、缺失模态识别与时间尺度曲线。

模型卡的 joint schema head 与 Jev 独立问题声明不能互相替代。托管文档还说明媒体和问题占 context，余下空间不足时截断文本 state；无论正确或失败都应保留这项条件。[模型卡](https://huggingface.co/Cloudflare/clef-omni) · [托管输入限制](https://developers.cloudflare.com/workers-ai/models/clef-omni/)

**状态：研究设计；没有启动 Live session、生成媒体题本或验证自托管与托管实现一致。** 视频采样率需要检查选定 revision 的实际实现；本轮没有将未核定的“2 fps”写成能力事实。

## 怎样选择下一次采集

先用离线 validate/demo/import/replay 验证题本和评分能区分正确、错误、缺失与拒答。采集前明确 provider、model、题本、重复数、总请求/问题上限以及输入边界。并排比较原始重复波动、干预变化、简单基线；不从单次稳定答案推出普遍不变性。

模型采集需要单独的操作者选择和调用上限。题本能准备请求、导入能解析响应、synthetic 能触发反例，分别证明这些局部路径；它们都不证明账号可用、服务价格、真实质量或生产收益。
